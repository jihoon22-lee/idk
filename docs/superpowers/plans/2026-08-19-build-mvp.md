# idk build CLI MVP Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** gcc/clang/CMake/make/Qt 빌드 로그의 핵심 진단을 파일 또는 stdin에서 추출해 plain/JSON으로 출력하는 `idk build` MVP를 제공한다.

**Architecture:** 파서는 외부 I/O가 없는 line-oriented state machine으로 만들고, 진단 model과 renderer를 분리한다. CLI는 입력 선택·필터·exit code만 담당한다. 첫 릴리스에는 build command 실행 감싸기, source preview, editor 실행, clipboard, TUI를 넣지 않는다.

**Tech Stack:** Python 3.10 stdlib parser, Typer, pytest; 런타임 의존성 추가 없음

**Spec:** `docs/plan.md` §앱별 설계 4와 `docs/superpowers/plans/2026-08-19-immediate-roadmap.md`의 `v0.2.0` 신규 기능 작업군

> 완료 기록 (2026-08-20): Task 1~5의 build MVP 구현·문서·smoke 준비는 통합 브랜치에서 완료됐다.
> 아래 Task 6은 당시 폐쇄망 acceptance 이후에 계획한 태그/배포 절차를 보존한다. 이 문서는
> 그 시점의 실행 계획 기록이며 현재 태그/Release 상태를 정의하지 않는다.
> 각 Task 제목의 상태 표기가 원래 단계별 체크리스트보다 현재 진행 상태의 기준이다.

## Global Constraints

- parser/model은 Typer/Rich/Textual을 import하지 않는다.
- 입력은 `--file` 또는 stdin 중 정확히 하나이며 전체 로그를 메모리에 복제하지 않는다.
- 원본 진단 순서를 보존하고 인식하지 못한 줄 때문에 전체 파싱을 실패시키지 않는다.
- plain 출력은 pipe 친화적이고 JSON schema는 테스트로 고정한다.
- 실제 로그 반출을 전제하지 않고 합성 fixture로 시작한다.

- [ ] **Step 3: immutable model과 compiler 정규식을 구현한다**

```python
COMPILER_RE = re.compile(
    r"^(?P<path>.+?):(?P<line>\d+)(?::(?P<column>\d+))?:\s*"
    r"(?P<severity>fatal error|error|warning|note):\s*(?P<message>.*)$"
)
```

path는 greedy match로 Windows drive colon과 상대/절대 경로를 보존한다. line/column은 int,
column 누락은 None이다. severity는 `fatal error`, `error`, `warning`, `note` 네 값으로 정규화한다.

- [ ] **Step 4: include/template context state를 붙인다**

`In file included from`, 이어지는 `from ...`, `required from`, `instantiated from` 줄은 pending
context로 모아 다음 error/warning에 tuple로 붙인다. note 진단은 독립 진단으로 보존한다. 빈 줄이나
새 primary diagnostic 뒤에는 잘못된 이전 context가 새 진단으로 넘어가지 않게 한다.

- [ ] **Step 5: parser 단위 테스트를 실행한다**

Run: `uv run --python 3.10 pytest tests/test_build_parsers.py -q`

**Files:**

- Create: `tests/fixtures/build/qt-tools.log`

**Interfaces:**
- Extends: `parse(lines: Iterable[str]) -> ParseResult`
- Preserves: Task 1 `Diagnostic` schema

- [ ] **Step 1: 합성 fixture와 expected diagnostics를 쓴다**

포함할 최소 형태는 다음 네 가지다.

```text
CMake Error at CMakeLists.txt:42 (add_executable):
make[2]: *** [CMakeFiles/app.dir/build.make:76: app] Error 1
src/widget.h:18:1: error: Meta object features not supported for nested classes
uic: Error in line 9, column 4 : Unexpected element widget
```

make line은 path/line이 없는 `tool="make"`, CMake는 파일/line과 multi-line message,
Qt compiler-style line은 `tool="qt"`, uic는 tool/line/column을 보존한다.

- [ ] **Step 2: fixture 테스트가 실패함을 확인한다**

Run: `uv run --python 3.10 pytest tests/test_build_parsers.py -k 'cmake or make or qt' -v`

- [ ] **Step 3: parser rule을 순서가 명시된 작은 함수로 추가한다**

`_parse_compiler`, `_parse_cmake`, `_parse_make`, `_parse_qt`는 각각 `Diagnostic | None`을 반환한다.
compiler-compatible Qt 줄보다 구체적인 Qt 규칙을 먼저 적용한다. CMake 본문은 다음 빈 줄 또는 새
marker까지 context에 붙인다.

- [ ] **Step 4: false positive와 손실 허용 테스트를 추가한다**

일반 `error count: 0`, 소스 코드 안 문자열, ANSI color가 섞인 줄을 다룬다. ANSI CSI sequence는
매칭 전에 제거하되 message의 일반 Unicode와 탭은 보존한다. 알 수 없는 줄은 diagnostic을 만들지
않고 `total_lines`에는 포함한다.

- [ ] **Step 5: 전체 parser 테스트를 실행하고 커밋한다**

### Task 3: plain/JSON renderer ✅ 완료

**Files:**
- Create: `src/idk/build/render.py`
- Create: `tests/test_build_render.py`

**Interfaces:**
- Consumes: `Sequence[Diagnostic]`
- Produces: `render_plain(diagnostics: Sequence[Diagnostic]) -> str`
- Produces: `to_payload(result: ParseResult, diagnostics: Sequence[Diagnostic]) -> dict[str, Any]`

- [ ] **Step 1: plain과 JSON golden 테스트를 쓴다**

plain 한 줄은 `path:line[:column]: severity: message`이며 source path/line이 없는 진단은
`[make] error: ...` 형식이다.
context는 바로 다음 줄에 `  | ` prefix로 출력한다. JSON top-level은 다음으로 고정한다.

```json
{
  "total_lines": 12,
  "diagnostic_count": 1,
  "diagnostics": [
    {"path":"src/main.cpp","line":12,"column":7,"severity":"error","message":"...","context":[],"tool":"compiler"}
  ]
}
```

- [ ] **Step 2: renderer를 구현하고 snapshot을 통과시킨다**

Rich markup이나 색을 넣지 않는다. TTY 색상은 후속 기능이며 plain 출력은 그대로 grep/redirect할 수
있어야 한다. JSON은 `ensure_ascii=False`로 한글 경로를 보존한다.

- [ ] **Step 3: renderer 테스트를 실행하고 커밋한다**

Run: `uv run --python 3.10 pytest tests/test_build_render.py -q`

```bash
git add src/idk/build/render.py tests/test_build_render.py
git commit -m "feat(build): render diagnostics as text and json"
```

### Task 4: `idk build` CLI ✅ 완료

**Files:**
- Create: `src/idk/cli_build.py`
- Modify: `src/idk/__main__.py`
- Create: `tests/test_build_cli.py`

**Interfaces:**
- Produces CLI: `idk build [--file PATH] [--format plain|json] [--severity all|error|warning] [--exit-code]`

- [ ] **Step 1: 입력·필터·exit code 행렬 테스트를 쓴다**

`--file`과 stdin은 각각 성공해야 한다. 둘 다 제공하거나 TTY에서 둘 다 없으면 exit 2다.
`--severity error`는 fatal error/error, `warning`은 warning, `all`은 note까지 출력한다.
`--exit-code`가 있을 때 필터 전 전체 결과에 error/fatal이 있으면 1, 그렇지 않으면 0이다.

- [ ] **Step 2: streaming input과 CLI wiring을 구현한다**

파일은 `open("r", encoding="utf-8", errors="replace")`, stdin은 `sys.stdin` iterator를 parser에
직접 넘긴다. CLI에서 `list(stream)`이나 `read()`로 전체 복제하지 않는다. `--format`과
`--severity`는 Enum으로 제한해 Typer가 잘못된 값을 exit 2로 처리하게 한다.

- [ ] **Step 3: root command에 lazy 등록한다**

`__main__.py`에 `app.command("build")(cli_build.build_cmd)`를 연결한다. parser/model 모듈은
Typer를 import하지 않고 CLI module만 import한다.

- [ ] **Step 4: CLI 테스트와 root help 테스트를 실행한다**

Run: `uv run --python 3.10 pytest tests/test_build_cli.py tests/test_cli.py -q`

- [ ] **Step 5: Task 4를 커밋한다**

```bash
git add src/idk/cli_build.py src/idk/__main__.py tests/test_build_cli.py tests/test_cli.py
git commit -m "feat(build): add file and stdin diagnostics command"
```

## 후속 기능의 측정 기반 진입 조건

- 실제 로그에서 중요 진단 recall이 충분한지 수동 확인한 뒤 새 parser fixture를 추가한다.
- `idk build -- <command>`는 stdout/stderr 순서 보존과 원래 process exit code 계약을 별도 명세한다.
- TUI는 source preview에 필요한 파일 접근·경로 해석이 검증된 뒤 별도 계획으로 만든다.
- 폐쇄망 로그는 반출하지 않고, 누락된 패턴의 비민감한 한두 줄 형태만 손으로 옮겨 synthetic
  fixture로 재작성한다.
