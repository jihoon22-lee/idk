## 목적과 확정 범위

폐쇄망 개발자가 기존 csh/tcsh 명령·`.csh`·편집기·Git을 유지하면서
프로젝트 선택 → 여러 터미널 준비 → 개발·빌드·테스트 → Git 검토/커밋 → 재접속·종료를
낮은 학습 부담으로 수행하도록 새로 설계한다.

프로젝트는 주 Git 저장소, 공통 개발환경, 소스/외부 테스트 경로의 이름 있는 터미널 묶음,
작업과 결과다. 대표 사례는 같은 소스 경로의 개발 터미널 2개와 서로 다른 외부 테스트 경로의
터미널 3개다. 5개는 최대 제한이 아니며 6번째 추가도 검증한다.

첫 공개 범위는 다음과 같다.

- 프로젝트 연결/최근 항목/개인 설정, 공통 `.csh` 초기화, 기본·임시 터미널 정의.
- 실제 터미널 입력·출력·재접속·소유권과 독립 셸 상태.
- Git 상태/diff/stage/unstage/commit/history/기본 branch/fetch/ff-only pull/대상 확인 push.
- 등록 빌드·테스트, bounded 로그·Problems·기존 편집기 이동, 결과물 관계의 확인/미확인.
- 오프라인 번들, 상태 보존, 현지 진단, 업데이트/복구.

GUI, 화면 분할·범용 레이아웃 편집, 새 셸/설정 언어, 내장 IDE/LSP/디버거,
고급 rebase·충돌 편집기·force push, 자동 패키지 설치·플러그인 마켓, 사외 통신·로그 반출,
legacy 전체 parity는 비범위다. 기존 linked worktree의 정확한 Git 대상 처리는 포함하지만
고급 worktree 생성/정리 UI를 요구하지 않는다.

## 기술 결정과 원본 보호

Rust + Ratatui/Crossterm + 검증된 PTY/화면 라이브러리 + 필요한 동안 동작하는 사용자 host는
후보다. 채택 스택·crate/version·target/ABI·배포 형태는
[WP01](../plans/v0.4.0/WP01.md)의 실행 검증과 ADR 대기다.
Zellij/tmux 학습이나 기존 Python/pyz 재사용을 필수로 하지 않으며 자체 터미널 엔진이나
여러 backend를 동시에 지원하는 framework를 먼저 만들지 않는다.

새 코드의 경계·검사·문서는 B01에서 실제 코드와 함께 정한다. 기존 Python 유지보수에는
기존 규약을 적용한다. 구 구현을 지워 규약 충돌을 해결하지 않는다. 사용자 소스·`.csh`·Git
저장소·기존 설정은 자동 삭제·변환하지 않는다. 요청된 정상 Git 작업은 그 범위에서 수행한다.
이전 공개 릴리스와 Git history는 보존한다. importer는 필요한 최소 범위·충돌 정책을
별도로 정의하며 원본을 보존한다.

## 승인된 작업·공개 순서

2026-09-07 사용자는 v0.4 구현·검증·릴리스까지 진행하고, **릴리스된 결과물로 폐쇄망 실기를
이후 직접 수행**하도록 지시했다. 이 지시는 원격 #38~#47의 “폐쇄망 실기 완료 후 공개”
순서를 변경한다. 기능 요구사항이나 결과를 PASS로 변경하는 승인은 아니다.

1. 각 B 묶음에서 구현·회귀/실패 검증·실제 csh/PTY/Git 검증·문서를 함께 준비한다.
2. 지원 개발 환경의 실제 후보 패키지 실행·복구·보호·공개 전 검사를 완료한다.
3. 병합 및 필요한 CI 후 정확한 main SHA의 미공개 후보를 생성/선정하고 provenance를 고정한다.
4. 해당 후보의 공개 전 검사를 통과하면 승인된 범위에서 **같은 bytes**를 태그/릴리스로 공개한다.
5. fresh-download로 이름·크기·digest·기본 실행을 확인한다.
6. 사용자가 공개 결과물을 폐쇄망에 반입해 대상 RHEL/정책 실기를 수행한다.
   허용된 판정만 수용 원장에 연결한다. 미실행·실패·확인 불가는 그대로 남긴다.

폐쇄망 실기 미실행은 이번 공개의 선행 blocker가 아니라 **공개 후 사용자 후속 작업**이다.
릴리스가 게시되어도 “대상 RHEL 검증 완료” 또는 “폐쇄망 최종 수용 PASS”로 표시하지 않는다.
공개 전 필수 구현/패키지/보호 검사의 실패는 이 조정으로 면제되지 않는다.
이미 승인된 구현·공개에 반복 승인을 요구하지 않되, 폐쇄망 설치·정책 변경까지 개발 에이전트가
대신 수행하는 권한으로 확대하지 않는다. 공개 RC를 별도로 만드는 절차는 기본에 추가하지 않는다.

원격 이슈에는 이전 순서가 남아 있다. 주 에이전트가 동일 승인 내용을 #38/#39/#47과
관련 WP의 공개·수용 문구에 동기화해야 한다. 이 문서 작성 자체는 원격 변경이나 공개 결과가 아니다.

문서 전용 PR을 의무화하지 않는다. 인접 묶음 병합이나 결함 수정 PR을 허용한다.
추가 분리는 데이터 손실·보안·복구 위험 또는 검토 가능성의 근거와 실제 mapping을 기록한다.
복잡한 독립 조사·검증·리뷰는 범위와 완료 조건을 정해 위임하고 같은 파일 동시 편집을 피한다.

## 증거와 변경 관리

[수용 원장](../acceptance/v0.4.0.md)에 R01~R18/S01~S08, 후보/공개 bytes, 공개 전 결과,
공개 후 실기를 연결한다. 요구 변경은 명세·관련 WP·검증 항목·원격 진행 원장을 함께 갱신한다.
내부 명칭은 “폐쇄망”으로만 적는다. 원문 소스·로그·경로·계정·증거 파일은 반출하지 않는다.
마스킹·요약·hash가 반출 허가를 만들지 않으며 허용된 판정도 확인할 수 없으면 확인 불가다.
