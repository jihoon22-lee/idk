# v0.4.1 — 타임아웃 취소 복구와 공개 기록 정리

v0.4.0의 자동 타임아웃 취소에서 `runs.json` 저장이 실패하면 메모리에만 `Cancelling`이 남아
타임아웃 검색과 host 재시도에서 제외됐다. 저장 경로가 복구돼도 작업이 계속 실행됐다.
사용자 요청에 따라 수정·문서·버전 갱신을 하나의 PR로 묶고 v0.4.1을 공개한다.
관련 요구는 R11/R14, 시나리오는 S05/S07이며 기존 B05/B06의 실패·복구 경계를 보완한다.

## 변경

- `RunRegistry::cancel`은 저장 실패 시 이전 `RunInfo`를 복원한다. 다음 timeout sweep에서
  재시도하며 취소 의도가 durable하게 저장되기 전에는 소유 프로세스를 정리하지 않는다.
- `host_runs`에 정상 timeout과 저장 실패 후 자동 복구 검사를 추가했다. 실제 저장 오류가
  host에 표시되는 것을 기다리고 heartbeat 증가로 선행 signal이 없음을 확인한다. 저장 경로를
  복구한 뒤 사용자 cancel 없이 `Cancelled`·timeout 의도·cleanup의 메모리/ledger 기록을 확인한다.
- Cargo 제품 버전은 0.4.1이다. 설치 fixture는 현재 버전과 다음 patch를 사용해 버전 변경으로
  원래 검증 대상이 downgrade/equal-version으로 바뀌지 않게 했다. 설치 제품 로직은 변경하지 않는다.
- 명세·WP08·수용 원장의 대기 표시를 실제 v0.4.0 공개 증거와 연결하고 공개 후 결함을 별도 기록했다.
  현재 README/반입·설치 예시와 CHANGELOG는 0.4.1을 안내한다. 데이터 schema·protocol 변경은 없다.

## 실제 검증

- 새 저장 실패 회귀를 **공개 v0.4.0 binary**(`71a5a25e4445086ce1c0a43adbe3ca2ab72a9e447c2d212fe7553900736fa93a`)로 실행:
  저장 복구 후 `Cancelling`, cleanup=false에서 15초 완료 대기 실패. 수정 전 결함을 잡는 검사임을 확인했다.
- 수정한 tcsh host_runs 12 + run_core 17 PASS. 정상 timeout과 자동 복구, 기존 수동 취소 저장 실패와
  종료 기록 복구, 실제 source gate 및 qmake/make·CMake·외부 Python 경로를 포함한다.
- WSL/Linux, 고정 Rust 1.97.1: workspace 204 PASS. 별도 실행 대상 PTY4·package1은 이 수에 포함하지 않는다.
- 실제 BSD csh의 csh_init11·project_flow13·run_core17·host_runs12, 총53 PASS. 실제 tcsh PTY4 PASS.
- fmt/Clippy(workspace/all-targets, warnings denied) PASS. Python 3.10/3.14 각각 packaging10·release13 PASS.
  Ruff check/format PASS.
- 독립 검토에서 cancellation rollback·직렬 worker·durable cleanup 경계와 문서 링크를 확인했다.

전체 검사의 첫 실행에서는 버전 고정 설치 fixture 5개가 실패했다. 현재/다음 버전으로 수정한 뒤
204개 전체가 통과했다. 실패 검사를 삭제하거나 downgrade 보호를 완화하지 않았다.

## 공개와 인계

최종 PR CI, main SHA의 새 후보와 패키지 검증, 동일 bytes 게시 및 새 다운로드 확인은 완료 후
이 PR의 실제 공개 기록에 연결한다. 이 문서는 병합 전 검증 기록이며 아래 항목을 선행 PASS로
기록하지 않는다. v0.4.0 결과를 새 후보의 PASS로 재사용하지 않는다.

대상 RHEL·폐쇄망 정책 실기는 계속 미실행이며 [#53](https://github.com/jihoon22-lee/idk/issues/53)에
최종 0.4.1 공개 identity를 인계한다. NFS host state/runtime은 지원하지 않는다.
업데이트는 기존 host를 재시작하지 않으므로, 수정 적용에는 원래 generation으로 기존 작업과 host를
정상 종료한 뒤 0.4.1 entrypoint에서 새 host를 시작해야 한다. 기존 셸·Run·로그는 자동 삭제하지 않는다.
